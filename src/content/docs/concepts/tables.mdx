## Typed tables

A typed table has one column per top-level property of its JSON Schema, plus an `extra jsonb` column for fields without a column. A property typed `["number", "null"]` (one type plus `"null"`) gets a nullable column of that type, not a union. The `generic` table holds everything that matches nothing else.

Tables are created only by an admin, never automatically and never from unvalidated payload keys:

- by **registering a schema** ([`POST /schemas`](/docs/api-reference/operations/registerschema/)), or
- by **approving a proposal**.

[`POST /proposals/scan`](/docs/api-reference/operations/scanproposals/) clusters similar payloads in `generic` and proposes a table. Approving a proposal creates the table, moves the fitting rows over and turns on routing for that shape. Rejecting it discards the proposal. Schema changes add a new version and can only add columns.

All typed tables are range-partitioned by `created_at`, one partition per UTC day, created on demand.

### Registering a schema

[`POST /schemas`](/docs/api-reference/operations/registerschema/) (admin) takes a name, the table it creates and a JSON Schema 2020-12 object. Names are SQL-safe identifiers (letters, digits, underscore); top-level `properties` become columns.

```sh title="Register a schema"
curl -s -X POST "$GATEWAY/schemas" -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H 'Content-Type: application/json' -d '{
    "name": "weather_obs",
    "table_name": "weather_obs",
    "json_schema": {
      "type": "object",
      "properties": {
        "wind_ms":     {"type": "number"},
        "temp_c":      {"type": "number"},
        "observed_at": {"type": "string", "format": "date-time"}
      },
      "required": ["wind_ms"]
    }
  }'
```

The `201` response lists the version and the columns that were created:

```json title="201 response (shape)"
{
  "name": "weather_obs", "version": 1, "table_name": "weather_obs",
  "columns": [{"field": "wind_ms", "column": "wind_ms", "pg_type": "double precision"}],
  "auto_match": false, "catalog": "record"
}
```

By default a schema registered by hand is **not** auto-routed (`auto_match: false`): records reach its table only when they name it, with the `schema` field of [`POST /objects`](/docs/api-reference/operations/createobject/). Send `"auto_match": true` to route matching records to it automatically (per-record tables only; a bulk table answers 422). See [Auto-routing](#auto-routing).

Registering the same name again adds a new version that can only add columns. Records written under an older version read the missing columns as `NULL`. A new version keeps the previous version's `auto_match` unless the request sets it. For an auto-routed schema, registering the new version also moves the rows that now fit out of `generic`: see [Moving rows out of generic](#moving-rows-out-of-generic).

### Proposals

When many records land in `generic` with similar keys, an admin runs the scan and reviews what the gateway found:

<Steps>

1. [`POST /proposals/scan`](/docs/api-reference/operations/scanproposals/) returns the ids of new and refreshed proposals.
2. [`GET /proposals/{id}`](/docs/api-reference/operations/readproposal/) shows the clustered fields, the proposed `json_schema`, the fields it excluded and why, the row count and a few samples.
3. [`POST /proposals/{id}/approve`](/docs/api-reference/operations/approveproposal/) creates the table, moves the fitting rows over and turns on routing for that shape; the body can adjust the name or schema first. [`POST /proposals/{id}/reject`](/docs/api-reference/operations/rejectproposal/) discards it.

</Steps>

The admin console does the same on its Proposals page.

## Auto-routing

A payload sent without a schema name is routed to a typed table when it fits one that has **auto-routing** on: at least 80% overlap between the payload's top-level keys and the schema's properties (keys that cannot be column names are ignored), and the payload validates against the schema's latest version. The best-fitting table wins. Anything else goes to `generic`.

- **Approving a proposal turns auto-routing on** for the new table.
- **Registering a schema by hand leaves it off** unless the request sets `"auto_match": true`. This is deliberate: creating a table must not silently capture payloads that nobody sent to it.
- **A new version keeps the setting** unless the request sets `auto_match`. Routing always uses the latest version, so a version that is too strict (for example a field typed `string` that is sometimes `null`) sends those records to `generic` until you register a version that accepts them.
- **Bulk tables are never auto-routed.** They have no `generic` rows and are written with [`POST /tables/{table}/records`](/docs/api-reference/operations/createrecords/).

### Turning it on or off

[`POST /schemas/{name}/auto-route`](/docs/api-reference/operations/autorouteschema/) (admin) takes `{"enabled": true}` or `{"enabled": false}` and changes the flag on the schema's **latest version** in place. It is not a new version, and later versions keep inheriting the setting.

```sh title="Turn auto-routing on, and move the rows that already fit"
curl -s -X POST "$GATEWAY/schemas/weather_obs/auto-route" -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H 'Content-Type: application/json' -d '{"enabled": true, "backfill": true}'
```

- Turning it **on** never moves data unless you ask: `"backfill": true` also runs one bounded [backfill](#moving-rows-out-of-generic) step and returns `backfill: {moved, more}`.
- The response has a `warnings` list: other auto-routed schemas whose keys overlap this one's by at least 80%. They compete for the same records (the best match wins), so check them when you turn routing on.
- Turning it **off** sends new matching records to `generic` again unless they name the schema. Rows already in the table stay.
- A bulk table answers 409 and an unknown schema 404. Every change is audited as `schema.auto_route`.

In the admin console, the table page shows whether a table is auto-routed and has a "Turn on auto-routing" / "Turn off auto-routing" button next to "New version". Turning it on asks for confirmation, offers to move the matching rows from `generic` at the same time, and lists any overlapping schemas. The register form and the new-version page have a "Route matching records here automatically" checkbox.

## Moving rows out of generic

Records that did not fit when they arrived stay in `generic`. When a table can take them (a proposal was approved, or a new schema version accepts them), they can be moved into it. The move is permanent: the rows leave `generic`, and each object's catalog row now names the table and schema version. Digests, creation times and object ids do not change.

Only rows that **fit the schema's latest version** move (the same test as [auto-routing](#auto-routing)). Only live rows are touched, since `generic` holds no archived data. A row the database rejects stays in `generic`; that is not an error. Every backfill is audited as `schema.backfill`.

### Automatically

- **Approving a proposal** moves every fitting row in the same request, as before.
- **Registering a new version** of an auto-routed schema (inherited, or set with `auto_match: true`) runs one bounded step in the same request: at most 5000 rows are moved, and the response gets a `backfill` object, `{"moved": 283, "more": false}`. If `more` is `true`, there are still fitting rows; run the backfill again.
- Send `"backfill": false` with the new version to skip the automatic step (for example before a very large move you want to run at a quiet time).
- No automatic backfill happens for a first registration (use `"backfill": true` on [`auto-route`](#turning-it-on-or-off) to move rows into a new table), for a schema that is not auto-routed, or for a bulk table.

### Manually

[`POST /schemas/{name}/backfill`](/docs/api-reference/operations/backfillschema/) (admin) runs the same bounded step for the schema's latest version and returns `{"name", "version", "moved", "more"}`. Call it again while `more` is `true`.

```sh title="Move rows until nothing more fits"
while :; do
  out=$(curl -s -X POST "$GATEWAY/schemas/ais_watch_static/backfill" -H "Authorization: Bearer $ADMIN_TOKEN")
  echo "$out"
  echo "$out" | grep -q '"more":true' || break
done
```

It answers 404 for an unknown schema, and 409 for a bulk table and for a schema that is not auto-routed (a table nobody routes to should not collect unnamed payloads): turn auto-routing on first, with `"backfill": true` if you want the rows moved in the same call.

In the **admin console**, the table page has a "Move matching rows from generic" button next to "New version" (typed, auto-routed tables only), which asks for confirmation and repeats until nothing more moves or a safety limit is reached. The "New version" page offers a "Skip backfill" checkbox, and shows how many rows moved with a "Move more" button while `more` is true.

From the **command line**, `php bin/backfill <schema-name>` inside the container (or locally against `DATABASE_URL`) loops the same step until `more` is false. It writes the same `schema.backfill` audit rows, with method `CLI`.

<Aside type="note">
Running it twice is harmless: the second run finds nothing that fits and moves 0 rows.
</Aside>

## Bulk tables

Bulk tables are for high-rate streams (for example vessel positions). Register a schema with `catalog: "table"` to get one. Owner, source and label are fixed for the whole table (the label must name a built-in or registered [label policy](/docs/concepts/labels-and-binding/#label-policies); the default is `PUBLIC` / `UNMARKED`), and no catalog row is written per record. [`POST /tables/{table}/records`](/docs/api-reference/operations/createrecords/) ingests up to 1,000 records per call, all or nothing.

Bulk records have no per-record digest, metadata or label, and cannot be deleted individually. They are read with [`GET /tables/{table}/rows`](/docs/api-reference/operations/listrows/), not `/objects`.

```sh title="Register a bulk table"
curl -s -X POST "$GATEWAY/schemas" -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H 'Content-Type: application/json' -d '{
    "name": "position", "table_name": "position", "catalog": "table",
    "owner": "feed-gateway", "source": "ais-feed",
    "json_schema": {"type": "object", "properties": {
      "mmsi": {"type": "integer"}, "lat": {"type": "number"}, "lon": {"type": "number"},
      "sog": {"type": "number"}}}
  }'
```

```sh title="Send a batch"
curl -s -X POST "$GATEWAY/tables/position/records" -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' -d '{"records": [
    {"mmsi": 257123456, "lat": 63.43, "lon": 10.39, "sog": 11.2},
    {"mmsi": 257654321, "lat": 63.44, "lon": 10.41, "sog": 0.1}
  ]}'
```

```json title="201 response"
{"table": "position", "count": 2, "object_ids": ["01a1...", "01a1..."]}
```

The batch is all or nothing: one invalid record rejects the whole call with 422 and nothing is written.

## Reading rows

[`GET /tables/{table}/rows`](/docs/api-reference/operations/listrows/) reads a typed table across both tiers (see [Tiers and archive](/docs/concepts/tiers-and-archive/)), ordered by `(created_at, object_id)`. Filters are query parameters: `<column>=<value>`, `<column>.<op>=<value>`, `extra.<key>=<value>`, and the underscore-prefixed `_source`, `_owner`, `_id`, `_created_from`, `_created_to`, `_select`, `_order`, `_after` and `_limit`. The [reference](/docs/api-reference/operations/listrows/) has the operators and limits.

Operators are checked against the column type, and a typo gives 422 rather than returning everything. Timestamps without an offset are UTC. Each item has the catalog fields, `data` (the columns) and `extra`.

```sh title="Read a table"
curl -s -G "$GATEWAY/tables/position/rows" -H "Authorization: Bearer $TOKEN" \
  --data-urlencode "mmsi=257123456" \
  --data-urlencode "sog.gte=5" \
  --data-urlencode "_created_from=2026-11-10T00:00:00Z" \
  --data-urlencode "_created_to=2026-11-11T00:00:00Z" \
  --data-urlencode "_select=lat,lon,sog" --data-urlencode "_limit=100"
```

```json title="200 response"
{
  "table": "position",
  "items": [{
    "object_id": "01a1...", "created_at": "2026-11-10T08:00:12+00:00",
    "owner": "feed-gateway", "source": "ais-feed",
    "label": {"policy": "PUBLIC", "classification": "UNMARKED"},
    "digest_sha256": null, "schema_version": 1,
    "data": {"lat": 63.43, "lon": 10.39, "sog": 11.2}, "extra": {}
  }],
  "next": "eyJ..."
}
```

Pass `next` back as `_after` for the following page.

Things to know:

- Only `created_at` is indexed. Give a time range on big tables.
- Files written under an older schema version read the missing columns as `NULL`.
- At most 31 archive files are opened per request, so a page can be short and still carry `next`. Follow `next` until it is `null`.
